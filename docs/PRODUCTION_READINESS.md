# Production readiness — 22 September 2026

**Status: not ready for general production distribution on macOS and Windows.** The frozen **0.4.0-beta.2** source passes its full test suite and build, including image/CAPTCHA and execution-receipt changes. Its packaged macOS app also passes all three native workflows. The Windows package has been cross-built, but not run on Windows. Distribution and live-service acceptance gates remain open. Neither the earlier v0.3.0 nor beta.1 benchmark measures this changed candidate.

This independent review inspected source, CI, lockfile, package metadata, release hashes, signing metadata and recorded evaluations, without runtime edits. Its initial source snapshot was around **12:39 UTC** while implementation was changing. A subsequent explicitly authorized **single live vision request at 12:54 UTC** is recorded separately below; it used an owned synthetic image in an isolated Electron test, not an external CAPTCHA. Production means a versioned, supportable browser distributed to ordinary users on both requested platforms; a local unsigned preview has a narrower acceptance bar.

## CAPTCHA proof needs a precise claim

The solver checks that the *same observed anchor and response element* changes from an empty to a non-empty response value. It does not emit the token. `CHALLENGE_ACCEPTED` correctly describes a new widget response, rather than server-side verification. This is a useful local signal, but the field belongs to the embedding page: a value appearing there does not prove that the site's server accepted the response, that its protected action succeeded, or that the user's whole task completed.

Its visibility/occlusion checks remain bounded observations: a tiny overlay can fall between sampled points. The opaque-background fix addresses host content visible through a transparent child, as demonstrated by the separate pixel tests above. The single real-model synthetic-image test is transport evidence, not proof of arbitrary-page screenshot isolation.

Hidden research-source views have an explicit current limitation. The final native smoke verifies that inspection runs while the new source is actually hidden; when its viewport is too small for the widget, Jevry takes a conservative handoff. It performs no screenshot capture, vision/Jev call, native input, submission or fabricated acceptance in that branch, retains the source, and brings its tab forward without reporting completed research. This is verified hidden-view refusal and recovery, **not automatic solving inside a hidden view**.

False-completion tests must therefore distinguish three results: model-proposed input, new widget response, and a separately observed protected-page outcome. A challenge disappearing, a model saying “done,” or a host script writing a response field must not become a claim of accepted server verification. The normal engine already keeps `verified:false` unless an independent outcome check is supplied (`engine.ts:419–426`); preserve that distinction in the UI and follow-up summaries.

Provider isolation has meaningful tests: strict bounded image input, selected model preserved, no text-only fallback, no executable tools, API error sanitization, ephemeral Claude sessions, Codex private temporary image cleanup, and cancellation drainage. Together with the single live Claude crop test, this establishes the mocked contracts and one actual Claude vision path. It does not establish that every connected model accepts vision or solves a particular challenge. Fresh CLI installation/authentication and each advertised real-provider path still need platform evidence; current CLI installation also requires a usable npm installation when the provider is absent (`providers.ts:300–323`).

## Existing controls and documented limits

The production blockers above do not negate the security controls already present. Remote tabs use `WebContentsView` with sandboxing, context isolation and Node integration disabled (`main.ts:150–157`). Browser permission requests/checks are denied (`main.ts:652–659`), and IPC handlers accept only the application window's main frame (`main.ts:410–415`). The renderer has a restrictive script CSP. Page evaluation uses app-owned scripts in a named isolated world with a unique context ID (`native-evaluator.ts:90–110`), avoiding a previously found navigation/lifecycle race. Keys, conversations and workspace data use OS-backed encryption and temporary-file rename writes. These are source-level controls with selected regression coverage, not a penetration-test certificate.

Some remaining limits can be stated honestly without blocking a constrained preview: permission-dependent websites cannot access denied media/location features; file uploads/download workflows, arbitrary cross-origin widgets, learned workflows and general irreversible transactions are not established capabilities; sensitive actions are conservatively handed to the user. Browser cookies persist in the app's own partition, and no clear-site-data control was found. A production privacy/recovery flow should make site-session deletion explicit; deleting a conversation or disconnecting a model does not erase website sessions.

## Competitive goal remains separate from release readiness

The [competitive review](COMPETITIVE_REVIEW.md) records the scope of every comparison. The deterministic executor result (**15/15 versus 6/15 upstream Jev**) measures those control fixtures with deterministic decisions, not live inference. The actual Firecrawl experiment uses its real source graph plus a declared local-browser/Claude bridge, not its cloud product. The three-repeat live fixture study is too small and narrow to establish global superiority or zero latency. A new beta.1 study met all 15 requested outcomes on each side after assistant review. Its five-turn median was 48.341s versus 52.782s, with Jevry lower on four tasks and higher on policy research. Two disclosed native-test overlaps and differing runtimes constrain interpretation. Beta.2 adds the pending-checkbox fix and has not been measured in that comparison; it must not inherit the prior build’s exact timings.

The genuine Ego host was downloaded and inspected. Its isolated launch did not establish disposable profile/launcher containment. Introduced integration entries were moved into reversible rollback, the exact mounted app process was stopped, and the DMG was detached; the cleanup record (local artifact: `artifacts/ego-isolation-attempt.json`) remains available. **There is no native Ego success or performance result.** A reliable contained genuine-host run is necessary to claim the original competitive goal is complete, but is not itself a prerequisite for shipping a correctly scoped browser preview.

The next review should start from a new frozen candidate, not accumulate old test counts or benchmark timings onto changed code. Clearing the explicit rows above, with links to their resulting artifacts, is the evidence required to change this status.
