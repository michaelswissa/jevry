# Jev game controller preview

[Game measurements and regression verification](GAME_RESULTS.md) distinguish the beta.4 controller and focus fixes from the earlier beta.3 gameplay measurements.

Jev chooses **every move** in the same finite operation/target request used for ordinary browsing. Native Electron/CDP executes that choice against the observed board. A quick demonstration uses `gameMode: demo`; playing toward a win uses `gameMode: win`; a bounded in-game objective uses `gameMode: task`. The latter retains visual map controls but checks the requested task contract, such as an observed construction queue, rather than requiring a full-match victory. Follow-ups retain the objective, success conditions and current page. A task contract distinguishes actual success from progress-only signals such as score; it is shared with ordinary website tasks (see [engine design](ENGINE.md)). Tutorial dismissal and board focus are ordinary setup actions.

Plain follow-ups such as `play` or `keep playing` reuse the saved game objective when the current URL still matches. They go directly to Jev without a fresh conversation-planning call. A changed page or an explicit new objective uses the regular planner. Pixel comparison also marks inputs that leave a calibrated board unchanged, even when unrelated page text changed.

Beta.7 makes the game mode explicit in the planning schema and repairs malformed plans once before execution, with feedback identifying the invalid fields. Schema repair and stream recovery share a maximum of two planning generations; neither can replay browser actions. A bounded game task retains map controls while requiring evidence for its specific outcome.

## Keeping the move loop fast

[Jev accepts text and JSON, not images](https://docs.typesafe.ai/concepts/system-one). For an unfamiliar canvas game, the connected vision-capable model provides reusable rules, tactics, supported controls and a grid calibration. It does not select a sequence of moves or dispatch inputs.

`desktop/game-perception.ts` learns cell appearances from that screenshot. Subsequent screenshots are classified locally into a fresh labeled board for Jev. Numeric templates compare numeral shapes as well as color. A validated 4×4 slide-and-merge schema enables local Tesseract OCR for new numbered tiles, using bundled language data and confidence/number validation. Unknown or unreadable values remain unknown. The reader follows board translation and proportional resizing; an incompatible layout still requires calibration.

For numeric merging games, the controller copies only the board from Electron’s native surface once calibrated, locally retries animated frames, and checks the expected merge/spawn transition before deciding it needs another visual review. Cropped and full-frame coordinates share one tested mapping. Other grids retain local pixel matching and a bounded animation retry; non-grid games rely more on visual review. Same-goal follow-ups in the same tab and conversation retain the calibration and learned numeral appearances, while a new document invalidates them.

Each move still requires one Jev network request. For a single board, keyboard target selection is deterministic, so the request contains no redundant target questions for each key. The executor focuses the board without dispatching an extra click, then checks keyboard focus; unrelated text changes elsewhere on the page do not discard a valid board input. Demonstrations normally need no visual model and must send at least eight keyboard inputs before reporting completion. They compare local board screenshots to detect ineffective keys, temporarily removing those choices until the board changes. Because animation can obscure a no-op, short demos also require a different input after three identical consecutive keys. Jev chooses the alternative. This demonstration rule does not restrict winning strategies.

There is no predetermined winning sequence or access to hidden game variables. Pixel templates, local OCR, cached strategy, recent outcomes and current page text supply Jev's state. Performance reports separate visual setup, Jev decision latency, native input time and total turn time.

The live answer reports the largest observed tile against its target; it never treats cumulative score as tile value. When the target tile appears, further move choices are suspended while victory is checked.

For the `slide_equal` rule family, `desktop/slide-merge.ts` simulates each legal input and uses bounded expectimax lookahead to estimate future position quality under the declared random spawn distribution. It supplies all candidates, their resulting boards, merge gains, empty-cell counts, estimated values and ranks. Jev makes the actual finite choice on every move; local code never dispatches a choice without that response. The normal move request contains one operation question and compact game state, without unrelated page controls or repeated prose tactics. These forecasts are estimates under learned rules, not independently verified future outcomes or a universal game solver.

When rules are unclear or earlier strategies failed, the visual analyst can request a public guide lookup through the same background-help capability used by ordinary website tasks. Guides, solutions, built-in hints, undo and single-player shortcuts may inform its strategy; they cannot authorize unrelated actions or turn a fabricated score into success. The guide is cached with the game context and Jev still chooses native input.

When observed keys leave the board unchanged, Jev receives the ineffective keys and the remaining input choices. The analyst's tactics are advisory: a preferred corner or direction may be relaxed to make progress. Actual game rules and predicted collisions still constrain the choice. An unavailable preferred direction alone is not grounds to stop or pay for another visual review.

For regular boards, each pointer choice includes the row, column and diagonal facts that pass through it. When visible rules describe discrete movement, the analyst can provide a small validated movement schema: player labels, static obstacles, hazard movement and key displacements. Local code computes destinations and predicted collisions for Jev to compare. These are learned-rule predictions, not an independently verified physics model; Jev selects the action. The schema contains data only and cannot execute code.

## Execution and completion

Supported game inputs are arrows, WASD, Space, Enter and guarded board clicks. Grid cells become finite, labeled point choices with coordinates derived locally from the observed board rectangle. The executor also supports bounded key holds (up to one second), but the current strategy offers single presses, not sustained real-time control. It always releases a held key during cancellation and preserves its key-down receipt.

Blocking semantic dialogs preempt game calibration and input, including dialogs in a parent page above an embedded game. Jev receives the observed popup controls and their context immediately, chooses an authorized close/skip/decline or relevant game-panel action, then gets a fresh observation before play resumes. Closing optional onboarding is already covered by a request to play; accepting purchases, premium-currency offers or permissions is not. A game's own containing dialog does not block its board. Covered coordinates are checked again immediately before native input. Canvas-drawn overlays still require visual interpretation; the controller does not blindly close every dialog or click through an overlay.

Rendered custom DOM controls (for example a div with a pointer cursor or keyboard focus affordance) are offered alongside native buttons. The snapshot excludes canvas wrappers and duplicate text/icon descendants; native input still uses the same fresh hit test. This permits ordinary decline links in custom game offers without site-specific selectors or coordinates.

Beta.6 gives visual calibration the same full surface geometry used for native input, including supported same-origin iframe offsets, borders and scrolling. Previously the visual reader discarded iframe canvases even when the normal action snapshot offered them. A free-form map uses labeled visible point candidates plus ordinary observed controls; it does not need a fabricated grid. Point targets must exactly match an offered surface, with x/y fractions relative to its full rectangle. Invalid coordinates receive specific bounded repair feedback. If the repair still contains bad optional points, those points are discarded while valid candidates and ordinary controls remain usable; malformed analysis never establishes victory. External-help analysis uses the same repair path.

For uncalibrated scenes, a changed surface fingerprint now requests fresh visual analysis immediately. Grounded point candidates remain available on an unchanged scene after input, avoiding the previous gap where points expired after one action but routine visual review waited eight actions. This adds necessary vision work on changing maps and does not imply the numeric game's per-move speed. Regular grid matching and the numeric merge fast path remain separate.

Beta.8 fixes an additional live-map stall: refreshing DOM guards after a slow visual call could detect an animated map and restart analysis before the first input. The engine now permits one immediate handoff of that completed analysis with fresh controls, provided document/viewport identity, surface nodes and full geometry are unchanged and no input intervened. Popup checks and native hit testing still run; changed geometry and subsequent map inputs require the normal review. This prevents an analysis loop, not the need to interpret changing maps.

Beta.9 supplies the visual analyst with current ordinary click targets and their viewport rectangles, including iframe offsets. It may label an observed icon (for example a construction hammer versus a previous-province arrow) through `controlLabels`. Jev receives those labels on the existing finite choices. Annotations cannot create targets, expire after input, and are dropped if the node, original label or rectangle changes. Purchase checks consider both the original and visual label. Invalid optional labels share bounded analysis repair and are discarded if still invalid.

Beta.10 also grounds unlabeled DOM controls when a game panel covers every canvas. Such scenes use a viewport fingerprint and ordinary click targets, with no invented map surface. This handles information and construction panels whose icons otherwise lost visual context after the map disappeared.

Beta.11 keeps clearly labeled DOM actions on Jev's fast path. If Jev selects an ambiguous icon without recent visual context, the engine obtains that context before dispatch; an icon-only obstacle can also request visual recovery. A named decline control does not require a visual call merely because other icons are present. Analysis receives the exact available operation names; invalid optional policy entries share bounded repair and are filtered instead of aborting the entire turn.

Beta.12 checks a bounded game task immediately when visual analysis reports its requested objective reached, before more orders or cleanup clicks. The contract check uses a fresh observation and bounded, exact visible-line citations. Unrelated countdown changes no longer restart the whole strategy: completion may proceed only when every selected citation remains present, the full document/frame/control page key is unchanged, and tables and collections are unchanged. Changed or missing proof and navigation require a new assessment. Earlier explicit post-action observations can support a result with provenance; an attempted input or filled form cannot. Ordinary website completion keeps its existing freshness behavior. Failed task checks invalidate the visual completion gate so recovery remains possible.

Beta.13 also offers the visual analyst's current screenshot observation as explicitly labeled model evidence for game tasks whose results have no DOM text. This is only available from a successful review of the same document, full page key, action count and observed control scene, without an intervening overlay or invalidation. The final Jev check must still match the requested condition and scope; the visual description does not establish independent verification. Completion failures are included in subsequent visual-analysis context.

Native input checks document identity, visibility, clipping, hit targets and focus. A canvas without `tabindex` temporarily receives `tabindex="-1"` so focus actually moves off the previously selected button or field. Focusability is retained through the run so focus does not blink on every key. Cleanup at completion, failure or Stop restores only the attribute value the executor owns, using the original element reference. Preparation failures refresh before input; failures after dispatch never replay the move. Stop releases held keys and restores focusability. Focus redirected into a field blocks before dispatch and reports that no key was sent. After slow visual analysis, a fresh observation replaces stale page guards before Jev chooses a move. Point actions cannot bypass separately observed buttons or form controls. Model output never becomes executable code. Every consequential move receives a new observation and a new Jev decision.

`DONE` requires evidence of the requested objective; a higher score or a draw is not a win. Without a visible victory status, a completion request gets a visual objective check, limited to two such reviews. This remains a model judgment in production: results stay `verified: false` unless an independent outcome checker is supplied. Live acceptance tests additionally inspect the actual game's status. Winning runs normally default to 400 actions; a validated numeric merge game gets 2,500 because a fresh 2048 game typically needs far more than 400 inputs. An explicitly supplied budget remains authoritative, capped at 4,000 for win mode. Runs allow at most twice as many model decisions, three restarts and two Jev-requested recovery reviews. Stop cancels pending reasoning and prevents late responses from executing.

## Evidence and limits

The mixed fixtures in `tests/games/` exercise canvas board clicks and keyboard strategy:

- Three in a row starts from a rotated winning position. The controller must identify the correct square and reach the actual victory state.
- Cross the road requires avoiding moving hazards and reaching the goal. Traffic advances only on input; this tests discrete arcade decisions, not reaction time in a continuously running game.

Native tests cover trusted key events, board clicks, focus theft, covered/disabled boards, modal interruption, cancellation, receipts and stalled boards. The beta.4 regression tests reproduce win-mode input on a canvas without `tabindex`, with prior button or field focus and page changes during visual analysis; they also exercise preparation recovery, Stop before dispatch, and non-replay after key-down or key-up transport failures. Strategy tests cover calibration, moved pieces, unknown appearances, animation settling, invalid targets, malformed analysis and keeping demonstrations entirely on Jev.

Beta.6 native regressions cover nested iframe map geometry, clipping and stale/unsupported frame rejection. A separate engine fixture starts with an invalid point, repairs it, then executes two trusted map clicks and two ordinary order-panel clicks through a bordered iframe. It verifies the actual rendered outcome and exact input receipts. Its model replies are injected; it proves execution/recovery mechanics, not live Supremacy strategy or a multiplayer win.

Later native regressions cover parent/child dialogs, custom decline controls, overlays arriving after selection, refusing purchase controls, an animated map with a changing HUD, and visual labels selecting the correct unlabeled icon through an iframe. These also use injected model replies; live recognition must be checked separately.

These tests do not establish a general win rate. Unreadable tiles or incompatible layouts can still require visual recalibration. The numeric fast path requires a validated 4×4 equal-value merge rule set; other game families do not inherit its lookahead. Irregular boards, continuously moving objects, drag gestures, simultaneous keys, cross-origin/transformed frames and closed shadow roots remain limitations. Cached rules and forecasts can be wrong. One Jev network request per move still imposes a latency floor.

## Run acceptance checks

```sh
npm run build
node scripts/test-live-game.mjs --run-live --strategy-fixtures --output=artifacts/live-game-jev-fast-fixtures.json
node scripts/test-live-game.mjs --run-live --output=artifacts/live-game-jev-fast-2048.json
node scripts/test-live-game.mjs --run-live --win-input-regression --output=artifacts/live-game-win-focus.json
node scripts/test-live-game.mjs --run-live --win-input-regression --move-limit=80 --continue-to-win --output=artifacts/live-game-sustained-win.json
```

The fixture run uses real connected models and native Electron, independently checks both victory states, and requires Jev to choose every move. The public 2048 run tests the original browse/play request and a `play` follow-up, checking action receipts, tutorial dismissal and increased score. The win-input regression focuses a non-game button before each of the exact prompts `try to win this game` and `continue`, verifies both retain the win objective, and intentionally stops after the requested key count and a score increase. With `--continue-to-win`, the second turn must reach a visible winning state; it is not stopped at the demonstration count. Reports include source hashes, decision-model names, per-move timings, submitted forecast values, Jev selections and final screenshots. All use temporary profiles and consume the saved providers' usage. Set `JEVRY_PACKAGED_EXECUTABLE` to test a packaged app. Without `--run-live`, the script only reports connection status. Individual live results are not a comparative benchmark.
